DeepSeek v4-pro costs 3× more than Flash. You're not paying for intelligence.

13 Oct 2026 · EN

I ran the same prompt through deepseek-flash and deepseek-v4-pro — same thinking switch, same medium reasoning effort.

The answers were equivalent. Time to completion differed by 2.2×. Cost differed by 2.4×.

Then it got more interesting. At high effort, v4-pro burned its entire 6,000-token budget on internal reasoning and returned absolutely nothing.

Here's the setup, the numbers, and what I'd actually do with each model.

First: the cheap model is the new one

Most people assume pro is the flagship and flash is the trimmed-down version. The release dates say otherwise.

deepseek-flash deepseek-v4-pro
Actually is DeepSeek V4.1 Flash DeepSeek V4 Pro
Released 2026-09-10 2026-04-24
Context 1,000,000 1,000,000
Max output 384,000 384,000
Input modalities text + image text only
Reasoning yes yes

Flash shipped four and a half months later. This isn't large-vs-small. It's two generations sitting on one price sheet.

Worth noting on its own: only Flash accepts images. v4-pro is text-only.

The price gap isn't 3×, it's 4.4×

Official off-peak rates, USD per million tokens. Peak hours are 2× — that's Mon–Fri 01:00–04:00 and 06:00–10:00 UTC.

Input Output Cache hit
deepseek-flash 0.15 0.60 0.003
deepseek-v4-pro 0.66 1.98 0.022
Multiple 4.4× 3.3× 7.3×

Don't stop at input and output. The last column is what sets your bill.

In any agent workload — file reads, tool calls, multi-turn loops — the overwhelming majority of tokens are repeated context prefix, i.e. cache hits. Pro charges 7.3× more for that. The longer your conversation runs, the closer your real cost gets to that multiple, not to 3×.

The head-to-head

The prompt is a classic trap: "A farmer has 17 sheep. All but 9 run away. Then half of the remaining sheep are sold, and 3 more are bought. How many sheep now, and what's the most likely arithmetic trap here?"

I picked it deliberately — it tests whether the model notices a language trap, not whether it can compute.

Model / effort Wall time Reasoning tokens Answer tokens Cost
flash @ medium 18.1s 3,898 77 $0.0024
flash @ high 14.2s 2,953 77 $0.0018
v4-pro @ medium 39.0s 2,837 69 $0.0058
v4-pro @ high 81.5s 6,000 0 $0.0119

Both models got the same answer, and both correctly identified the same trap: "all but 9 run away" means 9 remain, not 9 left. Both landed on 7.5 sheep, which is the correct reading of a deliberately broken premise.

Pro was slightly tighter in prose — 69 tokens vs 77. That is not a capability difference worth 2.4×.

v4-pro at high effort thinks itself to death

That last row is the real finding. 81.5 seconds. 6,000 tokens. All of it consumed inside hidden reasoning. finish_reason came back as length, and the content was an empty string.

You pay 1.2 cents and receive nothing.

In an agent loop this is a nasty failure mode, because it isn't an error. Your program sees a successful API call, gets an empty string, and keeps going. Without an explicit empty-content check in your parsing layer, this bug lives quietly as "the model is flaky sometimes."

Practical takeaway: don't set v4-pro to high. Medium is enough, and it's cheaper.

When I'd actually use v4-pro

Four runs of a trick question are not evidence that pro is worthless. The task was easy and both models cleared it. What the pricing structure and the behaviour suggest:

Default to flash for: - Tool-calling loops, file reads and writes, code edits - Long-context conversations - Anything that needs image input (pro can't take it) - Anything you'll run dozens of times

Reach for v4-pro when: - The problem is genuinely hard: architecture calls, messy debugging, multi-step reasoning - It's a one-off you're willing to pay for "thinking longer" - Effort is pinned to medium

The decision rule is just: how many times will I make this call? Once — use pro. Dozens of times — use flash, because the difference becomes a rent-payment question.

Method and limitations

Laying out the method, including the parts that don't flatter the conclusion:

  • One run per configuration. Variance at this scale is large. Note that flash at high came in cheaper and faster than flash at medium — that's pure noise, not an argument that high is more efficient. To use any of this as a baseline you'd need ~10 runs and medians.
  • Unit prices come from a local snapshot of DeepSeek's official pricing page dated 2026-09-10. The third-party catalog models.dev lists v4-pro at 0.435 / 0.87 instead. The two sources disagree — trust your own invoice.
  • A trap question measures the floor, not the ceiling. It says nothing about how these models differ on problems that are actually hard. That needs a benchmark set like GPQA, which is a different project.

Two things I found the hard way

1. deepseek-chat and deepseek-reasoner are dead, and nothing tells you.

DeepSeek retired both IDs on 2026-07-24. They're gone from /models — but the API still answers them with HTTP 200, substituting deepseek-flash and quietly reporting the real model name in the response body's model field.

I verified this by calling the endpoint directly:

model sent          HTTP   model returned in body
deepseek-reasoner → 200 →  deepseek-flash
deepseek-chat     → 200 →  deepseek-flash

Many client libraries do the same substitution even earlier, before the request leaves your machine. Neither layer raises a warning.

Check what you're actually running: don't read your config file. Print the model field from the response — that's the server confirming what executed. It's the only trustworthy source.

2. Passing a provider name as a model name returns a 400.

deepseek is the vendor, not a model. Send it and you get:

The supported API model names are deepseek-flash, deepseek-v4-pro, but you passed deepseek.

Use an alias instead.

The short version: that 3× premium doesn't buy a smarter model. It buys longer thinking, a heavier cache bill, and a failure mode where the model reasons itself into returning nothing. Decide which of those you want before you pay for it.
