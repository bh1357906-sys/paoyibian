DeepSeek silently serves you a different model than the one you asked for

16 Oct 2026 · EN

I asked the API for deepseek-reasoner. It ran deepseek-flash instead.

No error. No warning. HTTP 200, a normal response, and a model that wasn't the one I requested. The only place the truth appeared was a field in the response body that almost nobody reads.

So I tested the whole surface. There are two layers of silent substitution on this path, and both of them are invisible by default.

Layer 1: the server does it, and tells you in a field you don't read

Direct HTTP requests to api.deepseek.com/chat/completions, one per model name:

Model name sent HTTP model field actually returned
deepseek-reasoner 200 deepseek-flash
deepseek-chat 200 deepseek-flash
deepseek-flash 200 deepseek-flash
deepseek-v4-pro 200 deepseek-v4-pro

Both retired IDs are gone from GET /models, which currently lists only deepseek-flash and deepseek-v4-pro. But the completions endpoint does not reject them. Send one and the server substitutes Flash, completes your request, and records the substitution in the response body's model field.

So there is no error to catch. It doesn't fail loudly or quietly — it just does a different thing than you asked, successfully.

Reproduce it yourself:

curl -s https://api.deepseek.com/chat/completions \
  -H "Authorization: Bearer $DEEPSEEK_API_KEY" \
  -H "Content-Type: application/json" \
  -d '{"model":"deepseek-reasoner","messages":[{"role":"user","content":"say OK"}],"max_tokens":10}' \
  | grep -o '"model":"[^"]*"'

I can't tell you whether this is a deliberate compatibility layer or unintentional soft-landing, or when it started. What I can tell you is that model is the only signal, and most clients never look at it.

Layer 2: your client library does it too, earlier

Same problem on the client side. I asked a local agent tool to run deepseek-reasoner. It answered normally. Then I checked its usage log:

session_id               model            calls
20261015_210739_2016eb   deepseek-flash   1

The tool rewrote the model name before the request left my machine. Its source carries the mapping directly:

# DeepSeek retired deepseek-chat / deepseek-reasoner on 2026-07-24
_DEEPSEEK_RETIRED_ALIASES = {
    "deepseek-chat":  "deepseek-flash",
    "deepseek-reasoner": "deepseek-flash",
}

And here's the part worth sitting with: that comment says the retired IDs have returned HTTP 400 since 2026-07-24. My tests got 200. Either the API loosened up since, or the 400 only ever applied to a different path.

I don't know which. But it means the person who wrote the compatibility shim has an out-of-date model of what the API does today — and so, probably, do you.

Why both layers choose silence

In fairness, the design isn't malicious, and it's not stupid.

You ship a client. The vendor retires two model IDs. Thousands of your users have configs naming them. You have two options:

  1. Hard error. Every stale config breaks on upgrade. Users blame you.
  2. Silently map to the successor. Everything keeps working. It's just not the model they asked for.

Almost everyone picks 2. The problem isn't the substitution — it's that nobody tells you. A warning, a log line, a substituted_model field would cost approximately nothing and hand the user back their own decision. That's the part that got skipped.

Why this costs real money

Three concrete failure modes, roughly in order of how much they'll hurt:

1. Your cost model is wrong. If you budgeted for one model and you're running another, your numbers are off with no direction. When you go to optimize, you don't know what to optimize.

2. You misattribute quality changes. "The model got worse lately" is one of the most common complaints in this space. If your model silently changed under you, that observation may have nothing to do with model releases.

3. Capability assumptions break silently. Models differ in more than intelligence — image input, reasoning behaviour, context length. A pipeline written against model A's capabilities, running model B, fails in ways that look like intermittent weirdness rather than a bug.

How to check what you're actually running

In order of how much I'd trust each:

First, print the model field from the response. It's the only value the server signs its name to. If you've written your own client, this is one line. It eliminates an entire class of debugging.

Second, check your tool's usage log. A good tool records the model it actually used, and that record beats your config file — because config is intent and the usage log is fact. In one local agent it lives in a SQLite table called session_model_usage.

Third, diff your config against the provider's live /models. If you're configured for an ID that isn't in that list, you have a problem. This is scriptable and worth running regularly.

And the general rule: don't trust your config file. It records what you wanted to happen, not what happened. This entire post exists because those two things diverged and nothing raised a hand.

This isn't a DeepSeek problem

DeepSeek is just the one I happened to hit. The same pattern shows up whenever a provider retires a model ID, and it usually appears in two places at once: a server-side compatibility layer, and a mapping table in your toolchain. Both can be silent. Stacked, that's two places you have to suspect.

The transferable rule is one line:

The only truth about which model ran is in the response, not in your config.

Method notes, including the parts that don't flatter the conclusion: the API behaviour above is a live test run on 2026-10-15 with a personal key, not a reading of the docs; the table contains raw return values. The client-side mapping is quoted from source, with the file identified.

What I could not determine: when the server's 200 behaviour started, whether it's intentional, or whether it will change back to 400. Don't treat it as a stable contract if you're designing against it.
